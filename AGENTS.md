# Repository Guidelines

## Project Shape
- This is a Django invoices application with apps for accounts, invoices, expenses, backups, imports, and E2E validation.
- `app/` contains Django settings and URL entrypoints.
- `accounts/`, `invoices/`, and `expenses/` contain application code, migrations, templates, static source files, and tests.
- Source static assets live under app-level `static/` folders, especially `invoices/static/invoices/`.
- Django templates live under app-level `templates/` folders, especially `invoices/templates/invoices/` and `expenses/templates/expenses/`.
- Root `env.example` is the only committed environment example. Copy it to untracked `.env` for local work.

## Generated And Local Files
- Do not commit runtime databases, session state, generated static output, generated exports, screenshots, videos, or local env files.
- `db.sqlite3`, `db/e2e.sqlite3`, `db/e2e-runtime.sqlite3`, `*.profraw`, `.env`, `media/`, `node_modules/`, `test-results/`, and `playwright-report/` are local/generated.
- `staticfiles/` is generated by `collectstatic`; keep only `staticfiles/.gitkeep`.
- `tmp/` is for generated Playwright auth state, rendered invoices, template exports, and other temporary outputs; keep only `tmp/.gitkeep`.
- If a test needs fixture data, place a sanitized fixture under `tests/fixtures` or a clearly named app test fixture directory, not under `tmp/` or `staticfiles/`.

## UI And Product Rules
- Display monetary amounts consistently with two decimals; use helpers like `floatformat:2` in templates.
- Use Tabler Icons only when adding or updating UI icons.
- Treat Pico.css group components as the canonical pattern for grouped buttons, filters, and segmented controls.
- Use Charts.css for charts and data visualizations unless a task explicitly changes that design decision.
- Preserve existing design tokens and component styles in `invoices/static/invoices/css/design/`; avoid ad-hoc one-off styles when a shared component pattern exists.

## Development Commands
- Create a local env with `python -m venv .venv && source .venv/bin/activate`.
- Install Python dependencies with `python -m pip install -r requirements.txt`.
- Install Playwright package dependencies with `npm ci` when E2E tests are needed.
- Run migrations with `python manage.py migrate`.
- Run the local server with `python manage.py runserver`.
- Run a quick Django sanity check with `DEBUG=1 SECRET_KEY=dev-check DB_PATH=/tmp/invoices-check.sqlite3 python manage.py check`.
- Run Django tests with `python manage.py test`.

## Validation And Automation
- `scripts/ci.sh` is the canonical Docker-based validation entrypoint for automation; it builds the Docker test target and runs Django tests inside the container.
- `scripts/coverage.sh` runs the same test target under coverage for review automation.
- `scripts/e2e.sh` is the repo-owned Playwright smoke entrypoint. It creates/migrates `db/e2e.sqlite3`, seeds E2E data, starts Django, and writes Playwright auth state under `tmp/`.
- Do not add workflow-level browser/runtime install steps back into Gitea workflows for Playwright. Automation uses the shared Playwright evidence runner image; keep repo-specific E2E behavior in `scripts/e2e.sh`.
- Preview and artifact automation uses `scripts/preview.sh`, `scripts/destroy-preview.sh`, and `scripts/artifact.sh`.
- Production deployment uses `scripts/deploy.sh` and `scripts/verify_deploy.sh`; the live Ultramac stack stores persistent runtime data outside git under the `03-invoices` deployment folder.

## Managed Automation Files
- `.gitea/workflows/`, `project/opencode-managed.json`, `scripts/opencode`, and `scripts/lib/opencode-managed-workflow-context.py` are managed automation integration files.
- Do not edit managed automation files during ordinary product tasks.
- Only change managed automation files when the task explicitly targets automation setup, workflow behavior, repo onboarding, or chore synchronization.

## Database And Media Safety
- Local development SQLite should use `DB_PATH=db/db.sqlite3` or another untracked path.
- Production SQLite is bind-mounted at `/app/db/db.sqlite3` inside containers and is not the repo checkout DB.
- Uploaded media and backup outputs belong under untracked `media/` or the production bind mount, never in git.
- Never use production or customer data as committed test fixtures. Sanitize or synthesize fixtures before committing.

## Coding Guidelines
- Python target is 3.13; use PEP 8 style with 4-space indentation.
- Use `snake_case` for modules/functions, `CamelCase` for classes, and `UPPER_SNAKE_CASE` for constants.
- Keep business logic in services or model helpers when views/forms become complex.
- Add or update migrations when model fields change.
- Add focused tests for model, form, service, view, and import behavior touched by a change.

## Documentation And PR Hygiene
- Update `README.md` when setup, runtime behavior, deployment, validation commands, or operator workflow changes.
- Update the relevant file under `docs/` when development, deployment, backup, or automation behavior changes.
- Keep `DESIGN.md` aligned when UI foundations, visual language, or reusable component decisions change.
- Avoid reintroducing old root-level draft specs or one-off plans. Use issues/spec docs for task history and keep repository docs current.
- Commit messages should be imperative and concise, for example `Fix backup run timestamp display`.
- PRs should include verification steps, migration notes when relevant, and screenshots/videos for UI-visible changes.

## Security
- Never commit secrets, tokens, cookies, `.env`, Playwright auth state, or database files.
- Treat `tmp/playwright-auth-state.json` and similar browser state files as sensitive runtime artifacts.
- Use placeholders in examples and docs; do not include real customer names, invoice exports, credentials, or host-only operational secrets.
